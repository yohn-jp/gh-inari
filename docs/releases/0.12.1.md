# gh-inari 0.12.1

## Summary

0.12.1 is a reliability patch for the governed Change lifecycle
(`inari change issue|ready|abort`) and its trusted-executor evidence
pipeline. It fixes a set of related defects discovered while releasing
0.12.0: a failed self-dogfood coordinator run could crash before writing
any evidence, a trusted executor build failure was indistinguishable from
a semantic execution failure, a branch-only recovery state (created branch,
failed pull request) could not be cleaned up, a correlated but unsuccessful
Actions run could discard a valid semantic result, and provider failure
diagnostics were not consistently preserved. No CLI flag, schema, or public
export changed.

## Fixed

- The self-dogfood certification coordinator (`scripts/self-dogfood.mjs`)
  no longer crashes writing its own failure evidence when an `inari change
*` step fails after an earlier step already recorded a mid-lifecycle
  `ChangeState`; `finalState` is now reset to the `UNAVAILABLE` sentinel
  instead of retaining a stale, schema-invalid status (#499).
- `inari-change-executor.yml`'s build and execution steps are now
  separated into distinct fail-closed stages, so a build/setup failure and
  a semantic execution failure produce distinguishable, bounded results
  instead of collapsing into one opaque error (#502, #505).
- A Change stuck with a `CREATE_BRANCH`-only recovery state (branch
  created, pull request creation failed) can now be admitted and cleaned
  up by `change abort`; recovery planning only deletes the canonical
  branch in this case and continues to fail closed for ambiguous or
  unrelated evidence (#504, #506).
- A valid trusted semantic Change result -- including a `RECOVERY_REQUIRED`
  outcome -- is now preserved as authoritative even when its correlated
  Actions workflow run concludes unsuccessfully, instead of being reported
  as a transport failure; missing, malformed, or genuine runtime-failure
  artifacts still fail closed (#508, #510).
- Change effect provider failures (credential/scope, transport, provider
  HTTP, response validation) now carry bounded, typed, secret-safe
  classifications through the broker, issuer authority, trusted execution,
  and remote evidence contracts, instead of being flattened to a generic
  error; effect-level error codes are unchanged (#507, #511).

## Behavioral changes

None visible to callers of `issue`/`pr` `create`/`edit`/`normalize`/`sync`
or `inari change *`. The fixes change only how the trusted executor and
its evidence pipeline classify and recover from failures that were
previously misreported or unrecoverable.

## Upgrade instructions

```bash
npm install --global gh-inari@0.12.1
inari --version
```

Existing 0.12.0 installs upgrade with no required action. Repositories
using the governed Change lifecycle (`inari change *`) benefit from more
accurate failure reporting and from being able to recover a Change stuck
in the branch-only `RECOVERY_REQUIRED` state introduced by the defects
above.

## Breaking changes

None. `engines.node` remains `>=24`. No CLI flag, schema, or public
export changed from 0.12.0.

## Known limitations

Carried forward from 0.12.0 (see `docs/releases/0.12.0.md`): the Golden
Path architecture gate does not itself add a Golden Path CLI, runtime
orchestration code, or persistence store; the Cloudflare Worker deployment
holds no persistent session/policy store; strict one-shot/replay semantics
cannot be fully proven by a stateless signature alone; Issue relation
observation is read-only; and GitHub authentication/authorization remain
supplied by the caller's environment.
