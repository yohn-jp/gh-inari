# gh-inari 0.5.0

## Summary

0.5.0 is a robustness and reliability release: it closes a process-spawn
validation gap, prevents unbounded local and remote input from exhausting
memory, adds ReDoS protection to repository-authored PR policy patterns,
adds visibility into governed mutations that race with a repository
governance change, corrects CLI error classification for malformed
artifact numbers, and isolates unrelated template compilation failures
from unaffected `issue get`/`validate` calls. No new commands or
capabilities are introduced.

## Highlights

Two changes are CLI-visible and worth flagging explicitly; see
[Behavioral changes](#behavioral-changes) below:

- `gh inari issue|pr get|explain <n>` and `validate <n>` now reject a
  malformed artifact number with a distinct `INVALID_ARTIFACT_NUMBER`
  error instead of the generic `UNKNOWN_COMMAND`.
- `gh inari issue|pr create` JSON output now includes a `governance`
  field reporting whether repository governance was still at the
  validated generation immediately after the mutation completed.

## Fixed

- `ProcessGhTransport.run()` now validates `timeoutMs` before spawning
  the `gh` child process, matching the existing pre-spawn validation for
  output byte limits. An invalid timeout can no longer launch `gh`
  before being rejected.
- `GitHubAdapter` no longer permanently caches a transient `gh`
  availability or repository-resolution failure. A later retry can
  succeed instead of endlessly replaying a stale rejection; concurrent
  callers still coalesce onto a single in-flight check.
- Repository-governed template and policy blobs containing invalid
  UTF-8 byte sequences are now rejected with a clear error instead of
  being silently corrupted with replacement characters.
- Repository-authored PR policy `pattern` rules are now rejected at
  compile time if they contain constructs prone to catastrophic
  backtracking (nested quantifiers, alternation with overlapping
  literal text), closing a ReDoS exposure in PR field validation.
- `gh inari issue get`/`validate <n>` no longer fails for every issue in
  a repository when an unrelated Issue Form template fails to compile.
  Only the target issue's own template match, or genuine ownership
  ambiguity, affects the result; a failed sibling template is now
  surfaced as a bounded diagnostic instead of aborting the read.
- Local `--from <file>` input and piped stdin are now bounded to 1 MiB.
  Oversized input is rejected early (before being buffered in full)
  with a new `INPUT_TOO_LARGE` error instead of growing memory usage
  without limit.

## Behavioral changes

- `gh inari issue|pr get|explain <n>` and `validate <n>` (existing-
  artifact validation) reject a malformed artifact number -- `0`, a
  negative number, a non-integer, or a non-numeric value -- with a new
  `INVALID_ARTIFACT_NUMBER` error (exit code 2, validation-class)
  instead of the previous generic `UNKNOWN_COMMAND` (exit code 1,
  usage-class). Scripts that pattern-matched on `UNKNOWN_COMMAND` for
  this case must update to `INVALID_ARTIFACT_NUMBER`. `validate` used
  as a local template check (no artifact number, no `--from`) is
  unaffected.
- `gh inari issue create` / `gh inari pr create` JSON output gains a new
  `governance` field alongside the existing `ok`/`artifact` fields:
  `{ validatedGeneration, currentGeneration, reconciled, reason? }`.
  `reconciled: false` means repository governance advanced between the
  pre-mutation freshness check and the mutation completing; the created
  or updated artifact is never lost when this happens, and callers are
  not instructed to retry an already-successful mutation. Existing
  consumers reading `ok`/`artifact` are unaffected; consumers doing
  strict/exact JSON-shape matching should account for the new field.

## Upgrade instructions

Install the published package:

```bash
npm install --global gh-inari@0.5.0
```

Or install the extension directly from this repository:

```bash
gh extension install yohn-jp/gh-inari
gh inari --version
```

No template-format or governance-source migration is required for this
release.

## Breaking changes

None to command availability or successful-path output shapes. The two
entries under [Behavioral changes](#behavioral-changes) are additive or
reclassifying, not removing existing fields or commands; the
`UNKNOWN_COMMAND` to `INVALID_ARTIFACT_NUMBER` reclassification is the
only change a caller might branch on.

## Known limitations

- The supported Node.js range remains `>=22.13`.
- Unsupported GitHub-native fields and browser-only behavior continue to
  fail closed as documented in the main README.
- Repository-sourced governance requires the caller's authenticated `gh`
  installation.
- Local `--from <file>` and stdin artifact input are bounded to 1 MiB;
  a legitimately larger artifact document must be split or reduced
  before use.
