# gh-inari 0.8.0

## Summary

0.8.0 makes Inari ready for sustained dogfooding as the governed Issue/PR
artifact layer. All supported artifact inputs now converge through one
repository-governed canonical model, existing artifacts carry deterministic
template identity, partial and malformed inputs have bounded repair paths, and
callers can provide governed fields directly from the CLI without constructing
a complete JSON document.

## Highlights

- One canonical artifact ingress pipeline:
  - JSON, supported Markdown, existing GitHub artifact bodies, and direct CLI
    fields converge through the same candidate -> canonical contract ->
    canonical JSON boundary.
  - JSON is reloaded and validated rather than trusted merely because it is
    syntactically valid.
  - Equivalent supported representations converge to equivalent canonical
    semantics before rendering or mutation.
- Deterministic existing-artifact identity:
  - Newly rendered Issue and PR bodies include a bounded invisible template
    identity marker.
  - Valid markers select the repository-authoritative contract directly.
  - Legacy artifacts retain deterministic structural fallback and fail closed
    on zero or ambiguous matches instead of guessing.
- Direct governed CLI field input:
  - Repeatable `--field <name>=<value>` input is projected from the selected
    canonical contract rather than a handwritten second schema.
  - Scalar duplication, unknown fields, and `--from` / `--field` conflicts are
    rejected with bounded structured diagnostics.
  - List/checklist ordering is deterministic and partial edit/sync operations
    can use direct fields without a temporary JSON document.
- Canonical normalization and convergence:
  - Candidate values share field-aware normalization before semantic
    validation, including deterministic newline, Unicode, whitespace, and
    unsafe-control handling.
  - Partial inputs distinguish accepted, missing, and invalid fields while
    preserving accepted semantics.
  - Targeted repair merges only accepted replacements and rejects stale or
    incompatible repair context.
- First-class artifact repair and diagnostics:
  - Explicit PR template selection is authoritative for reconstructing
    repairable malformed or wrong-template bodies.
  - `normalize` and `edit` project failures through the shared bounded
    convergence diagnostic contract.
  - PR sync uses one canonical `--from` envelope contract for runtime
    validation, help, examples, and machine discovery.
  - PR render/parse round-trip validation remains mandatory and now reports
    bounded field-level semantic and metadata mismatches.
- Canonical rendering coverage:
  - Issue enum/multi-select values round-trip through governed native labels.
  - PR rendering is covered across native templates and the shared
    create/edit/normalize/sync paths.

## Upgrade instructions

Install the published package:

```bash
npm install --global gh-inari@0.8.0
inari --version
```

Existing complete valid JSON workflows remain supported. Callers may adopt
`--field` incrementally where direct semantic field input is more convenient.
New Inari-rendered artifacts will gain invisible template identity metadata;
legacy artifacts do not require migration.

## Breaking changes

No intentional breaking change to successful governed Issue/PR workflows.
0.8.0 is a minor release because it adds new CLI input and repair capabilities
and consolidates artifact handling around the canonical ingress contract.

## Operational guidance

Use Inari rather than raw `gh` for Issue/PR/template operations that Inari owns.
This release is intended to be exercised in normal repository work so remaining
UX defects can be found through dogfooding rather than by extending the
pre-release architecture further.

## Known limitations

- The supported Node.js range remains `>=22.13`.
- Free-form Markdown and natural-language semantic inference remain out of
  scope; unsupported or ambiguous representations fail closed.
- Template identity metadata never overrides current repository governance;
  unknown or stale identities are rejected.
- GitHub authentication and authorization remain supplied by the caller's
  environment.
