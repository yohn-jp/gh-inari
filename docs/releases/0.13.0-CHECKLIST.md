# 0.13.0 release checklist

This is the operator checklist for `gh-inari@0.13.0`. Machine-enforced workflow files remain authoritative.

## Release baseline

- Release staging branch: `release/0.13.0`
- Previous published baseline: `0.12.1`
- Target version: `0.13.0`
- Release tag: `v0.13.0`
- npm package: `gh-inari@0.13.0`

The staging branch was created before the final release-blocking changes landed. Do not tag its initial head.

## 1. Freeze the intended code

1. Merge the remaining release-blocking PRs to `main`.
2. Confirm their required CI/governance checks are green.
3. Update/rebase `release/0.13.0` onto the resulting exact `main`.
4. From this point, treat the branch as code-frozen except for release preparation or a release-blocking fix.
5. Record the exact baseline SHA in the release PR.

Do not silently absorb unrelated later `main` changes after the baseline is fixed.

## 2. Final contract review

Compare `0.12.1...release/0.13.0` and review only release-relevant public surfaces:

- CLI command tree, arguments, exit codes, and machine-readable JSON.
- `package.json` exports and npm bin aliases.
- MCP tool contracts.
- Implementation / Change / Session / agent-authority public contracts.
- README and bundled Skill guidance.
- Removed or deprecated compatibility surfaces.

Update `docs/releases/0.13.0.md` with concrete breaking changes and upgrade instructions discovered by this review.

## 3. Version synchronization

Set all version-bearing files consistently:

- `package.json`: `0.13.0`
- `.codex-plugin/plugin.json`: `0.13.0`
- `.agents/plugins/marketplace.json`: `^0.13.0`

Do not hand-edit generated lockfile version metadata inconsistently; use the repository's normal package/version workflow and inspect the resulting diff.

## 4. Local/package pre-flight

Run from the exact release branch:

```bash
pnpm install --frozen-lockfile
pnpm run verify
```

`verify` is the mandatory aggregate gate. Do not add unrelated tests during release preparation. A failure is either fixed as a release blocker or explicitly removes the candidate from release readiness.

Inspect the packed artifact produced by the package suite and confirm the installed package reports:

```bash
inari --version --json
```

Expected package version: `0.13.0`.

## 5. Required certification

Run only certification that is required by the current release governance / release-certification verifier. Certification must be bound to the exact frozen source SHA and packed/installed artifact.

If #449 or #689 is part of the agreed 0.13.0 release gate, execute it only after code freeze. Do not use a stale disposable fixture or repair product defects inside a certification task.

Retain bounded, secret-safe evidence.

## 6. Release PR

The release PR should contain only release preparation on top of the frozen product baseline:

- version synchronization;
- `docs/releases/0.13.0.md`;
- this checklist / release documentation;
- any generated metadata required by the repository.

Before merge:

- release PR governance is valid;
- required checks are green;
- release notes match the actual diff;
- no unresolved release-blocking review thread remains;
- the candidate SHA is known.

Merge through the normal governed PR path. No direct push to `main`.

## 7. Pin the release commit

After the release PR merges, capture its merge commit SHA:

```bash
git log -1 --format='%H %s' <release-merge-commit-sha>
```

The release target is this SHA, not whatever `main` happens to point to later.

## 8. Publish GitHub Release

Create the release explicitly against the pinned merge SHA:

```bash
gh release create v0.13.0 \
  --target <release-merge-commit-sha> \
  --title "gh-inari v0.13.0" \
  --notes-file docs/releases/0.13.0.md
```

Then verify `v0.13.0` resolves to that exact commit.

Publishing the GitHub Release triggers `.github/workflows/publish.yml`, which delegates to the organization npm publish workflow.

## 9. Verify npm publication

The publish workflow must complete successfully. It is responsible for version/tag verification, exact artifact packing/certification, smoke testing, and npm Trusted Publishing.

After success, verify the registry/package installation independently:

```bash
npm install --global gh-inari@0.13.0
inari --version --json
```

Confirm the reported version is `0.13.0`.

## 10. Close release

- Confirm GitHub Release points to the pinned release commit.
- Confirm npm contains `gh-inari@0.13.0`.
- Confirm installation and `--version --json`.
- Update/close the release tracking Issue/PR as appropriate.
- Delete `release/0.13.0` only after publication and post-publish verification are complete.

## Stop conditions

Do not publish when any of these is true:

- release branch is not based on the intended final `main`;
- version-bearing files disagree;
- `pnpm run verify` fails;
- required certification is missing or bound to another SHA/artifact;
- release notes materially disagree with the candidate;
- tag target is ambiguous;
- required GitHub checks are red;
- npm Trusted Publishing configuration is not ready.

A failed release attempt is not repaired by retargeting an existing tag to unrelated code. Fix through a governed PR and produce the next valid release candidate.
