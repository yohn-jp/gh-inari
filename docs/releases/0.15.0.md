# gh-inari 0.15.0

## Summary

0.15.0 establishes Inari's certified local execution plane as the normal local Agent path. The CLI now launches bounded Sessions through a persistent Admission service, Admission performs authorization and routes only authorized work to a separately running Executor, and provider credentials remain in Executor custody.

The release also includes the governance, lifecycle, transport, packaging, and reliability work merged since 0.14.1.

## Highlights

- **Local Admission and Executor golden path**: independent CLI, Runtime Authority, Admission, and Executor configuration/custody with the canonical local route `CLI / Agent -> Admission -> Executor` (#1018).
- **Local Session lifecycle**: `inari session start --issue <n> -- <command...>` creates or reuses a bounded Admission Session, injects only `INARI_SESSION_ID` into the child context, and `inari session close` closes the selected Session (#1022, #1029).
- **Credential isolation**: fresh local Session startup no longer requires GitHub provider credentials in the CLI. Repository identity is resolved through Admission and Executor, and GitHub/provider credentials plus Runtime Authority private material are excluded from the Agent child environment (#1061).
- **Post-admission execution boundary**: Executor accepts the bounded `AuthorizedExecution` contract rather than raw CLI intent or Agent Session authority; Admission owns Session validation and authorization (#1020, #1021).
- **Real-process certification**: canonical CI now exercises the actual CLI child, Admission HTTP process, and Executor HTTP process, including representative Change read/mutation and fail-closed denial paths (#1023, #1030).
- **Operator path**: the supported local setup and process sequence is recorded in the canonical operator documentation and continuously covered by `pnpm run verify`.

## Fixed

- Fresh setup now binds the actual Admission identity and endpoint into CLI configuration without manual JSON editing (#1061).
- Fresh Session repository resolution no longer falls back to a provider-credential-dependent CLI adapter (#1061).
- Agent children no longer inherit `GH_TOKEN`, `GITHUB_TOKEN`, Executor credential-file references, or Runtime Authority private-key material.
- Admission/Executor publication routing preserves the canonical normalized request fields required by authorization and execution.
- Local denial paths fail closed without invoking Executor for repository, task, capability, missing Session, closed Session, and expired Session mismatches.

## Behavioral changes

The normal configured local Change path is now explicitly:

`CLI / Agent -> Admission -> Executor`

Admission failure does not silently fall back to direct-App, Relay, user-token, or direct provider mutation. Explicit direct-App compatibility surfaces remain available during migration.

Local V1 remains loopback-only. Shared/Hosted Runtime onboarding is a separate programme and is not required for the local golden path.

## Upgrade

```bash
npm install --global gh-inari@0.15.0
inari --version --json
```

For a new local execution-plane setup, follow the canonical operator sequence:

```bash
export INARI_CONFIG_HOME="${INARI_CONFIG_HOME:-$HOME/.config/inari}"
inari init
inari setup --endpoint <repository-runtime-endpoint>
export INARI_GITHUB_APP_ID=123456 # replace with the numeric App ID printed by setup
inari executor setup
inari authority setup
inari authority bootstrap \
  --authority-id "runtime-<public-key-fingerprint-hex>" \
  --private-key "$INARI_CONFIG_HOME/authority/private-key.pem" \
  --max-session-ttl-seconds 3600 \
  --capability change.implement \
  --output "$INARI_CONFIG_HOME/authority/runtime-authority.json"
inari admission setup --from "$INARI_CONFIG_HOME/authority/runtime-authority.json"

inari executor serve
inari admission serve

inari session start --issue <number> -- <command...>
```

`inari setup` performs repository Runtime onboarding and GitHub App Device Flow.
It stores the App-user credential at `$INARI_CONFIG_HOME/app-user-credential.json`
by default (or the configured credential-file path). The local Executor is a
separate component: it reads that existing credential and requires the numeric
App ID in `INARI_GITHUB_APP_ID` or `GITHUB_APP_ID`. The `inari init` output
reports the credential custody path and ordered setup state, and after
`inari authority setup` it prints the exact Authority bootstrap and Admission
`--from` commands for the selected local key. Use the printed bootstrap
command's Authority ID, derived from the public-key fingerprint.

## Breaking changes

None.

This is a pre-1.0 minor release. The local execution plane becomes the canonical configured local path, while explicit compatibility transports remain available.

## Known limitations

- Local Admission and Executor V1 are loopback deployment surfaces; remote/public service authentication is outside this release.
- Shared/Hosted Runtime onboarding remains tracked separately and is not certified by the local execution-plane certification.
