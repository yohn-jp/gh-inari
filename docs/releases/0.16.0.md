# gh-inari 0.16.0

## Summary

0.16.0 completes the Local Runtime onboarding and operator experience introduced in 0.15.0. Local setup is now composed around dynamic runtime discovery, supervised Admission/Executor processes, a shared CLI/browser state projection, governed Runtime Authority bootstrap publication, and a strict separation between bootstrap user authority and normal Executor provider authority.

The release also restores package verification after the Runtime Authority publication-client removal so the release branch can certify the packed artifact against the current source tree.

## Highlights

- **Unified local setup state**: `inari init` projects the ordered setup path, current readiness, and next supported action from one canonical application-state model shared with the browser console.
- **Dynamic local runtime discovery**: Admission, Executor, and the local console allocate and publish dynamic loopback endpoints rather than relying on historical fixed ports.
- **Runtime supervision**: `inari runtime supervise` starts and monitors the local Executor and Admission as distinct processes with bounded startup/failure reporting and cleanup.
- **Browser and SSH operator path**: the local runtime console projects the same setup/runtime state as the CLI and emits the ready-to-use SSH forwarding command for loopback-only access.
- **Explicit non-loopback transport security**: non-loopback Admission/Executor deployment requires identity-pinned mTLS and fails closed on wrong-client, wrong-server, or missing transport identity.
- **Governed Runtime Authority bootstrap**: initial public Delegator trust publication is an explicit App-user-authorized setup operation and becomes canonical only after the governed publication PR is merged.
- **Executor Issuer authority**: normal post-bootstrap GitHub reads and mutations use repository-scoped Inari Issuer GitHub App installation credentials through the existing installation credential broker. App-user credentials are bootstrap-only.
- **Credential custody**: Admission and Agent contexts remain provider-credential-free; Issuer App private-key material is confined to the running Executor credential boundary.

## Fixed

- Removed stale package-suite expectations for the deleted `runtime-authority-publication-client` build outputs, restoring packed-file-set verification to the current source graph.
- Local Runtime setup no longer requires operators to manage historical/default internal ports.
- Supervisor startup failures no longer leave stale discovery announcements behind.
- Local Executor repository/provider access no longer depends on the operator App-user credential after bootstrap.
- Repository/App/installation identity and permission mismatches fail closed before provider mutation.

## Behavioral changes

The normal local authority flow is now:

```text
bootstrap:
operator CLI -> App-user credential -> governed Runtime Authority publication PR

normal execution:
CLI / Agent -> Admission -> Executor -> Issuer App installation credential -> GitHub
```

Bootstrap user authority and normal Executor provider authority are intentionally distinct. Admission remains the authorization boundary and does not receive GitHub provider credentials.

The supported product remains one `inari` distribution. CLI, Admission, and Executor continue to be distinct runtime roles behind that single operator surface.

## Upgrade

```bash
npm install --global gh-inari@0.16.0
inari --version --json
```

For a fresh local setup, start with:

```bash
inari init
inari setup --endpoint <repository-runtime-endpoint>

export INARI_GITHUB_APP_ID=<numeric-app-id>
export INARI_GITHUB_APP_PRIVATE_KEY_FILE=<path-to-inari-issuer-app-private-key.pem>

inari executor setup
inari authority setup
inari authority bootstrap \
  --authority-id <authority-id> \
  --private-key "$INARI_CONFIG_HOME/authority/private-key.pem" \
  --max-session-ttl-seconds 3600 \
  --capability change.implement \
  --output "$INARI_CONFIG_HOME/authority/runtime-authority.json"
inari admission setup --from "$INARI_CONFIG_HOME/authority/runtime-authority.json"

inari runtime supervise
```

Then launch governed work with:

```bash
inari session start --issue <number> -- <command...>
```

## Breaking changes

No intentional breaking change to successful 0.15.0 governed Issue/PR workflows.

This is a pre-1.0 minor release because it materially extends the Local Runtime onboarding, deployment, supervision, operator, and credential-authority model.

## Known limitations

- CLI, Admission, and Executor are runtime-separated but their compile-time/module authority boundaries are not yet fully enforced; follow-up architecture work is tracked in #1095.
- Explicit Direct-App and Hosted/Shared deployment surfaces remain separate from the Local Runtime golden path.
