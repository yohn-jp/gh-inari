## Known production blocker

The installed setup console has horizontal overflow at a 360 px viewport. Real Chromium measured a 360 px viewport and 369 px document width; the `.stepper` navigation extends to 367 px. The path is rendered in `apps/setup-console/src/view.ts` and styled in `apps/setup-console/styles.css`. Production code remains unchanged. The installed wizard certification continues through its independent controls and reports this condition as `PRODUCTION_BLOCKER`.

## Shared Setup first-publication blocker

Reproducer: `node --test --import tsx test/setup-application-certification.test.mjs` creates a temporary repository and credential, runs the packed `authority generate`, `authority bootstrap`, `authority register`, and legacy `setup` commands, then runs packed `setup next` for enrollment, migration and App binding. Before fixture merge, packed `setup status --json --repository cert-owner/renamed-project --repository-id 44332211` returns `stage: "unknown"`, repository-trust diagnostic `SETUP_TRUST_UNAVAILABLE`, and no `authority.publish-trust` action. `test/setup-browser-certification.test.mjs` observes the same state through the actual console.

Cause: `createAppUserSetupProvider.readCanonicalAuthorities` in `src/composition/setup-observation.ts` calls `loadDelegatorTrust`; `discoverAuthorityEntries` in `src/agent-authority/delegator-trust.ts` throws `RUNTIME_AUTHORITY_NOT_FOUND` for an empty protected-ref Authority directory. The provider maps that to an unavailable read, and `repositoryTrustStatus` treats it as unknown rather than untrusted. The action planner therefore cannot offer first publication. This is a production defect; the certification fixture and assertions do not change production semantics. The older packed `inari setup` path is independent and can publish the first PR. Browser and shared CLI trust recheck after the fixture merge pass, but first publication through those controls remains blocked.
